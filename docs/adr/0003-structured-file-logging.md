# ADR 0003: структурированные файловые логи

## Статус

Принято.

## Контекст

Подготовка медиатеки проходит через API, Celery worker, периодический
диспетчер и PostgreSQL. Одного статуса в `jobs` недостаточно для диагностики
очереди, внешних процессов и ошибок между стадиями. При этом логи не должны
содержать промпты, HTTP payload, query string или содержимое приватных медиа.

## Решение

- Python-процессы пишут одну JSON-запись на строку одновременно в stdout и в
  опциональный файл `LOG_FILE`.
- Файлы API, worker и scheduler разделяются Docker bind mount-ами и ротируются
  по размеру.
- PostgreSQL использует штатный `logging_collector` и суточную ротацию.
- Корреляция выполняется по безопасным идентификаторам: `request_id`,
  `task_id`, `job_id`, `asset_id`, `media_root_id` и `shot_id`.
- Логируются lifecycle HTTP/Celery и доменные границы стадий: начало,
  измеримый прогресс, итог, длительность и тип ошибки.
- Прикладные события используют единый контракт:
  `event = operation.status`, где `status` принимает значения `started`,
  `progress`, `dispatched`, `reused`, `retrying`, `skipped`, `succeeded`,
  `failed` или `cancelled`. Поле `stage` уточняет текущий технический этап.
- Текст сообщения строится в одном стиле: «операция начата», «этап завершён»,
  «операция успешно завершена» либо «операция завершилась ошибкой».
- SQL statements отключены в PostgreSQL-логах, чтобы не сохранять данные
  запросов при ошибках.

## Последствия

- Диагностика доступна как через файлы `logs/`, так и через
  `docker compose logs` для Python-процессов.
- Runtime-логи не версионируются Git.
- Файловая ротация worker рассчитана на текущий `WORKER_CONCURRENCY=1`. Перед
  увеличением числа процессов потребуется multiprocess-safe sink либо вывод в
  отдельный сборщик логов.
