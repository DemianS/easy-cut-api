# ADR 0002: подготовка медиакорня и восстановление фоновых задач

- Статус: принято
- Дата: 2026-10-16

## Контекст

Для полного индексирования одного медиакорня сейчас требуется вручную запускать
несколько задач для каждого видео. Celery повторно доставляет сообщение при
явной потере worker, но не восстанавливает запись `pending`, если сообщение не
попало в broker, и не знает предметных зависимостей этапов анализа.

## Решение

- Ввести родительскую задачу `library_preparation` и ссылку `parent_job_id` у
  дочерних задач.
- Запускать подготовку одной API-командой. Родитель задаёт желаемый результат,
  а короткая периодическая задача-диспетчер создаёт и отправляет готовые этапы:
  `library_scan`, `asset_probe`, `shot_detection`, `asset_description`,
  `asset_embedding`.
- Не удерживать Celery worker в ожидании дочерних задач и не полагаться на
  Celery canvas result backend.
- Тем же диспетчером повторно отправлять потерянные `pending` задачи и задачи с
  просроченным heartbeat. Число восстановлений ограничивать и хранить в БД.
- Запускать периодический диспетчер отдельным Celery beat-процессом. Docker
  продолжает отвечать за перезапуск упавшего процесса worker.
- Операции этапов остаются идемпотентными; диспетчер не перезапускает задачу с
  живым heartbeat.

## Последствия

- Пользователь получает один `job_id` для наблюдения за подготовкой папки.
- Состояние конвейера восстанавливается после перезапуска API, beat и worker.
- Между фактической потерей worker и повторной доставкой есть настраиваемая
  задержка.
- Некорректно выбранный слишком короткий timeout может привести к параллельной
  доставке долгой, но живой задачи, поэтому значения должны учитывать самый
  медленный локальный inference.
- На первом этапе визуальная часть конвейера обрабатывает только видео;
  изображения и аудио индексируются технически и явно учитываются как
  пропущенные.
